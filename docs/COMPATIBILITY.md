# 客户端版本与旧文件兼容

## 当前结论

实测版本是 **QQ 音乐 22.71 x86**。从 0.1.4 起，BetterDownload 不再用版本号或整个文件的哈希判断是否适配，而是按组件“去掉签名后的代码”识别：与 22.71 代码相同的版本直接适用，未实测的新组件在签名和接口检查通过后自动启用，并逐项校验结果。目前还没有其他客户端版本的实测样本。

| 层次 | 判断方式 | 当前验证 |
| --- | --- | --- |
| 解密算法 | QMC2（EncV1 / EncV2 ekey，映射与 RC4 两种变体），各版本相同 | 22.71 真实 FLAC 整曲；旧格式为原创夹具 |
| 旧文件格式 | QTag 与 QMC2 V1 的文件内密钥，不依赖客户端组件 | 原创 FLAC 夹具逐字节一致；没有旧客户端实测 |
| 本地密钥接口 | `CommonFunction.dll` 的代码哈希；未知代码须有腾讯签名和序号 12 导出，在子进程中调用并校验结果 | 22.71 x86 真实下载；隔离调用用原创替身 DLL 验证 |
| 新文件格式 | musicex V1 文件尾、对应资源密钥、完整音频校验 | FLAC 已实测；OGG 仅实现校验 |
| 下载完成事件 | 按导入名称观察 `QQMusic.dll`、`QQMusicCommon.dll` 的 Win32 文件复制 / 移动，不依赖代码地址 | 独立宿主验证四种操作；真实下载事件待联调 |
| QQ 内入口、设置和卡片 | `GF.dll`、`Common.dll` 的代码哈希；包装层须有腾讯签名和所需导出，未实测时在运行时检查对象 | 22.71 x86 已实机显示；未适配时的独立窗口有自动化检查 |
| 路径自动识别 | 默认下载目录、已有记录、新下载事件学习；启动时自动补处理 | 隔离夹具验证启动补处理、修改目录后学习及回填 |
| 安装与回退 | 用户目录版本文件、完整性校验、保留上一版、损坏回退及同版本修复 | 27 项隔离测试（含卸载时可选删除数据）；本机已安装，重启和升级全流程仍待验收 |

M4A、MP3 和 QMC1 暂未支持。支持旧文件格式不等于所有旧客户端均已适配。

## 为什么不用版本号或整文件哈希

22.71 安装目录中几个相关组件的 PE 编译时间和签名时间：

| 组件 | 代码编译 | 签名 |
| --- | --- | --- |
| `CommonFunction.dll`（密钥接口） | 2024-02-26 | 2026-09-09 |
| `mmkv.dll`（下载记录库） | 2024-02-28 | 2026-09-09 |
| `Common.dll` | 2025-04-27 | 2026-09-09 |
| `GF.dll` | 2025-05-15 | 2026-09-09 |
| `QQMusic_GFWrapper.dll`、`QQMusic.dll` | 2026-09-22 | 2026-09-22 |

腾讯签名的 58 个非本版编译的模块在 2026-09-09 统一重签，包括 2019 年编译的 `VMProtectSDK32.dll`。签名存放在文件里，重签后整个文件的哈希一定会变，代码却没有变。0.1.3 按整文件哈希判断，所以代码相同的其他版本也会被判为未适配。`QQMusic_GFWrapper.dll` 随每个版本重新编译，QQ 内界面在下一次小更新时必然停用。

现在的“代码哈希”是对整个文件做 SHA-256，但排除 PE 校验和、证书目录项和证书表，也就是 Authenticode 签名所覆盖的内容。重签不会改变它，代码的任何改动都会。实现见 `src/ClientCompatibility.cs`，它同时编进安装器，安装器显示的适配情况与程序运行时一致。

## 各时期客户端

据 [unlock-music 的说明](https://git.unlock-music.dev/um/um-react/src/branch/main/docs/faq_zh-hans.md)，Windows 客户端 19.43 及以前下载的歌曲在文件里自带密钥，其他版本需要另外取得密钥。本机的密钥接口和下载记录库都是 2024 年 2 月编译的，由此推测 19.51 之后的多数版本使用同一套代码，但还没有样本证实。

| 客户端 | 歌曲密钥来源 | BetterDownload |
| --- | --- | --- |
| 更早的 `.qmc0` / `.qmcflac` / `.qmcogg`（QMC1） | 固定算法，不需要密钥 | 暂未支持 |
| 19.43 及以前的 `.mflac` / `.mgg` | 文件尾自带 | 走旧格式路径，不依赖客户端组件；QQ 内界面按组件检查决定 |
| 19.51 起 | 本机 MMKV 库，库名和密钥由 `CommonFunction.dll` 按本机硬件生成 | 代码与 22.71 相同时直接使用；未实测但签名有效时自动启用并校验；否则保留任务 |

腾讯官方的旧版安装包地址（如 `dldir1v6.qq.com/music/clntupate/QQMusic_Setup_1943.exe`）目前均返回 404，第三方下载站的安装包无法确认未被改动，因此还没有做旧版实测。

## 未实测组件如何处理

### 本地密钥接口

1. `CommonFunction.dll` 的代码哈希在已验证列表中：在后台进程内调用序号 12 接口，与 0.1.3 相同。
2. 否则必须同时满足：有有效的腾讯签名，且存在序号 12 导出。签名离线校验，不检查吊销，也不联网。满足时在一次性子进程 `BetterDownload.exe --derive-store` 中调用。子进程在检查和加载期间拒绝其他程序写入该文件；崩溃或 15 秒无响应只结束子进程，不影响后台。
3. 返回值必须是 32 位十六进制密钥和普通文件名。
4. 下载记录必须完整解析，否则判为接口不符，新格式任务保留等待适配。每首歌解密后仍校验音频头和整曲，不合格不输出。

接口崩溃、签名无效或返回格式不符时，本次客户端运行期间不再调用；加载失败、超时等暂时性错误按 1、2、4…30 分钟退避重试。

### QQ 内界面

- 私有接口和虚表偏移都在 `GF.dll`、`Common.dll` 中，两者与实测代码一致才启用 QQ 内界面。
- `QQMusic_GFWrapper.dll` 每个版本都会重新编译。实测版本照旧直接使用；其他版本须有有效的腾讯签名，所需方法按 C++ 修饰名查找。修饰名包含参数和返回类型，签名一变就找不到。浏览器对象预留 4 KB（实测为 24 字节）。使用浏览器元素前，先检查它是有效对象，且要调用的方法都位于 `GF.dll` 或包装层的代码段内；不满足时不在 QQ 内显示设置页。
- QQ 的界面元素（`NavigationBar`、`RightFrame_Frame`）缺失时同样不接入。
- 界面不可用时，设置在独立窗口中打开（QQ 音乐窗口菜单 Alt+空格 → BetterDownload 设置），进度卡片显示在 QQ 音乐窗口右下角，设置页用一行说明哪一层未适配。任何情况下都不会自动弹出窗口。

## QQ 音乐更新时

程序和接入 DLL 安装在当前用户目录，后台代理从正在运行的 QQMusic.exe 获取实际路径。客户端安装目录变动后可重新识别，不需要依赖客户端更新时可能被移除的 msimg32.dll。下载接入只观察成功的系统文件操作，不依赖客户端代码的固定地址；保留已有第三方拦截，停用时恢复自己替换的导入项。

腾讯改动密钥方案（换接口、换存储或换签名主体）或重新编译 `GF.dll` / `Common.dll` 时，仍需发布适配更新。在此之前，新格式下载会保留，文件内自带密钥的旧格式照常处理，设置可在独立窗口中打开。

## 新增适配的验收依据

1. 在装有新版本的电脑上运行 `.\build\tests.exe --real-client <QQ 音乐安装目录>`。它报告各层识别结果，比较进程内调用与隔离调用的结果，不输出密钥和文件名。
2. 核对客户端架构、组件代码哈希、编译 / 签名时间、本地接口调用约定与存储结构；验证后把代码哈希加入 `src/ClientCompatibility.cs`。
3. 在真实下载完成后检查最终路径事件，不把“DLL 能加载”当成下载事件已验收。
4. 检查整曲音频、标签、可用的本地封面和源文件不变。
5. 检查重启、目录变化、缩放、停用和卸载；界面未适配时检查独立设置窗口和窗口右下角的卡片。
6. 分别记录真实客户端实测与合成夹具测试，更新本文件和验证记录。
